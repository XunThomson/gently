## 本轮目标（第一百一十五轮）

> 起点：R112 的前台服务让「熄屏还在放」成立，但通知栏只有一个「点一下回到应用」——
> 锁屏、蓝牙、耳机键都控制不了播放。P2-2 就是补这一半。

### 1. 本轮做了什么

| 层 | 改动 |
|---|---|
| Kotlin（`PlaybackService.kt`） | 接上 **framework 的 `MediaSession`**（`android.media.session`，API 21+，不引 `androidx.media` 少一条 Gradle 坑）：`MediaMetadata`（标题/歌手）+ `PlaybackState`（PLAYING/PAUSED + `PLAY/PAUSE/PLAY_PAUSE/SKIP_NEXT/SKIP_PREV`）+ `Callback`（onPlay/onPause/onSkipToNext/onSkipToPrevious）；通知改用 `Notification.MediaStyle`（`setMediaSession` + 三个按钮：上一首 / 播放·暂停 / 下一首，图标随 `playing` 切换） |
| Kotlin（`MediaActionBridge.kt`，新） | 原生 → 页面的**单向下发**：`Plugin.load(webView)` 里留 WebView 引用，按钮动作 → `evaluateJavascript("window.__gentlyMediaAction('toggle')")`。原生**不拥有播放状态**，只转发 |
| 宿主（`playback.rs` / `lib.rs`） | `playback_banner` 多一个 `playing` 参数（决定按钮图标与 `PlaybackState`） |
| 前端（`services/playbackBanner.service.ts`） | `syncPlaybackBanner(active, title, artist, playing)`；新增 `installMediaActionHandler()`：装 `window.__gentlyMediaAction`，**只在有宿主时装**，返回卸载函数。`useAudioEngine` 把它翻成 store 的 `toggle/next/prev`（与界面按钮同一条路） |
| 修复（本轮真机发现） | `active` 必须表示「**有没有当前曲目**」，不能等于 `playing`——第一版用同一个值，暂停就把前台服务连同 MediaSession 一起关了，之后耳机键/锁屏全部失效（GOTCHAS §60） |

### 2. 验证

- `pnpm typecheck` 通过；`pnpm smoke`：**539**（535 → +4：宿主里装上回调 / 三动作到得了前端且未知动作被忽略 / 卸载后全局函数被移除 / 无宿主是空操作）；
- **真机（`CDY-AN00`）**：

  | 项 | 结果 |
  |---|---|
  | 会话注册 | `dumpsys media_session`：`Media button session is com.xun.gently/gently-playback`、`state=PlaybackState {state=3 … actions=566}`（566 = play+pause+play_pause+skip_next+skip_prev） |
  | 暂停（媒体键 127） | 进度冻在 `6`；会话仍在（`state=2` PAUSED）——**这是修好 active/playing 之后才成立的** |
  | 播放（126） | `6 → 10`，会话回到 `state=3` |
  | 下一首（87） | 换歌（进度归 0 后重新走），通知标题跟着变成新曲目 |
  | 通知栏 | 三个按钮（⏮ ⏸ ⏭）；截图 `r115-android-notification.png` |

### 3. 未做 / 值得你知道的

- 通知小图标仍是系统自带的 `ic_media_play`（改成应用自己的需要加 drawable 资源）；
- `POST_NOTIFICATIONS` 运行时授权入口没有（API 33+ 不授权时通知不可见，但保活/媒体键仍生效）；
- `PlaybackState` 不带播放位置（`position=-1`）：位置不进原生，避免两处真相；锁屏进度条因此不显示；
- P4 通知栏歌词（可复用这套会话）、P3 余项（导入进度、清理已导入、`.m4s` 的 MIME）、
  R110 的「上游不是音频」进 UI 文案仍挂着。

## 本轮目标（第一百一十四轮）

> 起点：P0/P1/P2 都过了，手机上仍然只有一条「把音乐弄进来」的路——adb push。
> 这不是普通用户能做的事，等于「本地音乐」在手机上不可用。

### 1. 本轮做了什么

| 层 | 改动 |
|---|---|
| Kotlin（`gen/android/.../ImportPlugin.kt`） | `@Command pickAudio` → `ACTION_OPEN_DOCUMENT`（`audio/*` + 多选）；`@ActivityCallback` 里在**后台线程**逐个拷贝（`contentResolver.openInputStream`），同名不覆盖（`a.mp3` → `a-1.mp3`），回 `{imported, failed, cancelled, dir}`。SAF 不需要任何存储权限 |
| Rust 宿主（`src-tauri/src/importer.rs`） | 插件 `gently-import` 注册 Kotlin `ImportPlugin`，用 `run_mobile_plugin_async("pickAudio")`（异步：用户挑文件可能几十秒）+ `ImportOutcome` 结构体；`lib.rs` 新增宿主命令 `import_audio`。非 Android 如实回错（桌面端用「填目录」） |
| 前端 | `services/import.service.ts`（无宿主返回「取消」的空结果，浏览器里静默）；`ScanPanel` 在**手机形态**多一行「从手机导入音频」+ 说明 + 结果提示（已导入 N 首 / 部分失败 / 没读到音频 / 打不开选择器），导入成功后用返回的 `dir` 调 `library.local.scan` |
| 文案 | `page.local.importFromDevice/importing/importHint/imported/importedPartial/importEmpty/importFailed`（zh+en）；顺手修掉 `scanHint` 里那句已过时的「原生文件选择器需要额外的桌面插件」 |

### 2. 验证

- `pnpm typecheck` 通过；`pnpm smoke`：**535**（534 → +1「导入服务在无宿主时是空操作」）；
- **真机完整走查**（测试文件 `adb push` 到 `/sdcard/Download/import-test.mp3`）：
  1. 本地音乐 → 展开扫描面板 → 点「从手机导入音频」→ 系统选择器打开（「打开文件」：最近 / 音频 / 下载内容）；
  2. 抽屉 → 下载内容 → 只有 `import-test.mp3` 可选（其它非音频文件是灰的）→ 点选；
  3. 回到应用：提示「已导入 1 首」、「共 2 首」、列表出现 `import-test`；
  4. 磁盘：`run-as com.xun.gently ls -l files/music` → `import-test.mp3 4388383`；
  5. 入库：扫描结果「上次扫描 1 个文件，新增 1」；截图 `r114-android-import.png`。

### 3. 未做 / 值得你知道的

- **导入是「拷一份」**：原文件删掉不影响曲库；反面是占双份空间（后续可加「清理已导入」入口）；
- 选择器只过滤 `audio/*`：`.m4s`、少见的无损封装可能不在系统 MIME 库里（桌面端不受影响）——**R118 证实了这一点并修掉**；
- 多个大文件逐个拷没有进度条（只在结束后报数量）；P3 的其余部分（音乐目录授权、导出）未做。

## 本轮目标（第一百一十三轮）

> 起点：R112 的前台服务让「熄屏/后台还在放」成立，但 R111 记下的第三种形态仍然存在——
> 系统回收渲染进程后页面整页重载，内存里的 store 归零，用户回来只看到空播放条。

### 1. 本轮做了什么

| 层 | 改动 |
|---|---|
| 持久化（`utils/lastPlayback.ts`） | 新模块：`gently:last-playback` 存「一首歌 + 位置」；`parseLastPlayback()` **纯函数**做校验（坏数据一律当「没有」、位置夹在时长内、上限 1 小时）；只存恢复需要的字段（不存歌词缓存、不存队列） |
| 写盘（`player.slice.ts`） | `rememberPlayback()`：换歌与暂停恢复**立刻**写，位置每 `10s` 写一次（`setProgress` 每秒都在跑），`stop()` 清空（用户主动关掉的歌不该下次自己冒出来） |
| 恢复（`store/index.ts` + slice 初值） | `createPlayerSlice(ctx, readLastPlayback())`：曲目 + 位置装进**暂停态**（`playing:false`、`audioUrl:null`），并用 `candidatesOf(track)` 补一条候选——否则点播放会判「没有音源」 |
| 点播放（`toggle()`） | 新分支：「没有 `audioUrl` 的暂停」→ `recoverPlayback()`（重新解析、**保留进度**），不再把界面翻成「在播」却没声音 |
| 引擎（`audio.service.seek()`） | 不再在元素还没建时 `return`：恢复的调用顺序是「先 seek 再 load」，以前定位被丢掉，用户点了就从 0 播。现在走 `ensure()`，定位挂到 `loadedmetadata` |
| 测试 | 冒烟 +5：快照往返、坏数据一律当没有、位置夹在时长内、恢复态是暂停的、恢复的曲目**带候选** |

### 2. 验证

- `pnpm typecheck` 通过；`pnpm smoke`：**534**（529 → +5，全绿）；
- **真机（）冷启动续播**：播放到 `aria-valuenow=150` → `am force-stop` + `am start` →
  播放条显示 `probe`、位置 `150`、暂停态 → 点播放（核心日志 `媒体响应（本地文件） status=206`）→ `156/271`。
  截图 `r113-android-resume.png`；
- 两个坑都是真机才暴露的（都写进 GOTCHAS §59）：恢复的曲目**没有候选** → 点不动；
  `seek()` 在元素未建时 return → 从 0 播。

### 3. 未做 / 值得你知道的

- **不恢复队列**：队列可能上千条、来自随时会变的源；恢复一首歌 + 位置就够（`next` 在单曲队列里会停）；
- 「上次在放什么」是**跨设备无关**的本机偏好，存在 localStorage：清缓存/换设备就没了；
- P2-2（MediaSession + 通知栏传输控制 + 自定义通知图标 + `POST_NOTIFICATIONS` 授权入口）仍未做；
  P3 SAF 导入、P4 通知栏歌词、R110 的「上游不是音频」进 UI 文案也还挂着。

## 本轮目标（第一百一十一轮）

> 起点：R110 把「播不出声」定案成上游问题。剩下的真问题是 P2——
> 但计划里 P2 的入口条件写得很清楚：**先实测，再选路线**。本轮先测，再修测出来的 bug。

### 1. 本轮做了什么

| 层 | 改动 |
|---|---|
| 实测（P2 入口条件） | 真机（）播放 271 秒本地曲目 → 熄屏 → 定时用 `android-cdp.mjs eval` 读 `[role=slider]` 的 `aria-valuenow`。**三个包测出三种形态**：① R110 包：`4`→`33`→`171`，解锁回前台仍 `171`（音频停住）；② R111 首包：`4`→`56`→`226`，解锁后仍 `226`，元素 **`paused === false`** 也没报错（位置不动 = 僵死）；③ R111 带僵死看门狗：解锁回前台**进度是 `0`**——页面被系统整页重载，播放状态全丢。三种都不是进程死亡（`pidof` 一直没变） |
| 结论 | **P2 必须做前台服务（foreground service）+ MediaSession**，技术路线「WebView 播放 + 保活」；另有一条新发现：**页面被重载后播放状态全丢**，P2 落地时要持久化「上次在放什么 / 放到哪」并恢复 |
| 根因（第二层） | 形态 1 里 `HTMLMediaElement.play()` 返回的 Promise **既不 resolve 也不 reject**（探针挂到 CDP 超时都没回来）；旧代码 `await el.play()` 永远停在那一步，看门狗拿不到结论——不重载、不换源、不停表 |
| 前端（`audio.service.ts`） | 新增 `tryPlay()`：`play()` 一律带 **3 秒上限**（`ok / rejected / timeout`）；`resume()` 同套、超时算 `failed`；新增 `hardRecover()`（**先 reload 再 play**，治「以为在播、位置不动」）；`timeupdate` 里维护「位置采样」 |
| 前端（`utils/playbackStall.ts`） | 新增纯函数 `isStalled(previous, position, now, threshold)`：**只判 `paused` 会漏掉形态 2**，所以按「位置 8 秒没变」判僵死（正常缓冲抖动被阈值滤掉；倒退/前进都算在动） |
| 前端（`useAudioEngine.ts`） | 看门狗两条路：`isPausedNow()` → `resume()`；`isStalledNow()` → `hardRecover()`。都以「有 `MediaError` 给 2 次重新解析、只有超时/僵死给 1 次」收尾，仍不行 `markInterrupted()` |
| store / 文案 | 新增 `player.markInterrupted()`（**只停表、不换源**，曲目与候选都留着）、`PlaybackFailure.kind` 增加 `'interrupted'`、`playbackFailureText()` 三路分支、`player.failureInterrupted` 中英文案（「播放被系统中断（点播放继续）」）。点播放走既有 `retryPlayback` |
| 测试 | 冒烟 +3：`isStalled` 边界（动了/倒退/首次采样都不算）；三种失败各有文案且 `interrupted ≠ media`；`markInterrupted` 停表 + 写原因 + **曲目还在**（用例前后保存/复原 player 切片，不污染后面依赖候选列表的渲染用例） |

### 2. 验证

- `pnpm typecheck` 通过；`pnpm smoke`：**528**（525 → +3，全绿）；`pnpm verify` 8 道全绿；
- 真机三种形态的时间点与读数已逐条记进 `ANDROID-PLAN.md` §7.4（含 `pidof`、`ActivityRecord` 证据）；
- **诚实边界**：形态 3（页面被系统重载）下恢复逻辑没有机会执行——本轮的修复覆盖的是「页面还活着」的形态 1/2；
  让播放真正活下来要靠 P2 的前台服务。所以本轮的验证是「smoke 钉死逻辑 + 真机钉死现象」，不是「真机证明已修复」。

### 3. 未做 / 值得你知道的

- **P2 本体（前台服务 + MediaSession + 通知栏控制）还没做**：下一步在 `gen/android` 里加 Kotlin
  `Service` + 通知 + MediaSession，用 Tauri 的 `register_android_plugin()` 桥接（`run_mobile_plugin`），
  前端只在播放状态变化时推一次；这需要新增 Android 侧代码与 Gradle 配置；
- **播放状态持久化**（形态 3 暴露的）：页面被重载后要能恢复「上次在放什么 / 放到哪 / 暂停态」；
- 通知栏歌词（P4）依赖 P2 的前台服务；SAF 导入（P3）需要原生文件选择器；
- 「上游返回的不是音频」仍只进日志（R110 记的候选任务）。

## 本轮目标（第一百一十轮）

     要是你觉得别扭，我可以把这两条行为改成全身动作（`wave` / `inspect`），但那就丢了哭泣/等待的表情；
  2. 拖动动画临时用 `jump` 那一行（现有 9 个动作里最像「被拎起来」的），换更贴切的素材后只需要改一个常量；
- `fit` 是按**整行**缩放（不按帧），所以行内各帧的细微比例差还在；要更细就得给每帧单独的数据；
- 走动 / 看鼠标 / 自动穿透仍只在 Windows；
- 安卓仍按用户决定延后。
## 第一百零四轮

> 起点：R103 收尾时留下两处「没验证到的地方」——拖动的真实手感只能人工确认、
> 调试面板的「探测一帧」没能点中。本轮按「先把能自己验证的验证掉」推进：
> 把拖动的**结构性隐患**修掉，把调试面板做成**打开就自带数据**。

### 1. 本轮做了什么

| 层 | 改动 |
|---|---|
| 拖动（真凶） | 宿主每 60ms 按「光标是否在精灵矩形内」决定穿透；系统拖动时窗口位置更新滞后于光标，拖动头几十毫秒里光标已经出了矩形 → 窗口被切成 `ignore_cursor_events(true)` → 后续 `pointermove` 到不了 webview，拖动断在中间（用户感觉「拖不动 / 拖一半卡住」）。现在前端判定「开始拖」就先发 `gently:pet:dragging {dragging:true}`，`startDragging()` 返回后（或窗口失焦）发 `false`；宿主 `poll_once` 在 `DRAGGING` 期间**直接 return**（不切穿透、不自己走动） |
| 拖动（补收尾） | `startDragging()` 之后 `pointerup` 常常收不到，所以另加 `window blur` 兜底再发一次「没在拖」，避免宿主一直以为在拖（那会让宠物永久失去自动穿透） |
| 调试面板 | 展开面板就**自动读一帧**（`pet.tick{dtMs:0}`），不再要用户先点按钮；帧读数把动画**序号换成名字**（`animation=runRight(2)`，名字从 `pet.state` 的 spec 反查——没有单独的 `pet.get`）；新增「窗口开关」行（点击穿透 / 走动）；`probeOnce` 包了 `try/catch/finally`，**抛异常也显示出来**（调试面板最怕「点了没反应」） |
| 测试 | smoke 新增 1 项：宠物窗口 6 个事件名（含新的 `gently:pet:dragging`）都在 Tauri 接受的字符集内（GOTCHAS §31 那类「带点号事件整条丢失」的守卫）；smoke **502 → 503** |
| 测试抖动 | `oauth` 测试偶发 `连接本机回调端口` panic（回调监听线程绑端口是异步的，`begin` 返回后立刻 connect 会失败一次）→ 抽出 `connect_callback()` 最多重试 3 秒，不再用「sleep 一段时间再连」 |
| 文档 | GOTCHAS §39（拖动期间宿主必须停手）、§40（`ui:capture` 跑的是 `release/` 打包版 exe，改完代码要先 `pnpm package:portable`）、§41（回调端口测试要重试）；`pet.md` 调试面板一节补自动读帧与窗口开关 |

**P1-4 触摸语义**

| 项 | 决定 |
|---|---|
| 行内动作 | 手机上不渲染任何行内小按钮：`MobileRowActions` 是唯一入口，点开交给 `RowActionsProvider` 的**底部面板**（scrim + 抓手 + 48px 一行的动作，动作与桌面同源） |
| 面板宿主 | 挂在 `MobileShell` 外层（`<RowActionsProvider>` 包住 shell，面板是 shell 的兄弟节点）——放进带 `backdrop-filter` 的容器里会被当成包含块（GOTCHAS §54） |

### 7.4 R111：后台播放的实测（P2 入口条件）+ 中断恢复

> 计划里 P2 的入口条件是「先实测：锁屏 5 分钟 WebView `<audio>` 是否还活着」。
> 本轮把它做了，结论直接决定 P2 的技术路线。

| 项 | 实测 |
|---|---|
| 设备 / 包 | 真机 · Android 10 · `pnpm tauri android build --debug -t aarch64 --apk` |
| 步骤 | 播放本地 271 秒的测试曲目 → `svc power stayon false` + `KEYCODE_POWER` 熄屏 → 定时用 `android-cdp.mjs eval` 读 `[role=slider]` 的 `aria-valuenow` |
| 形态 1（R110 包） | 21:25:48 熄屏时 `4` → 21:26:17 `33` → 21:29:05 `171`；**21:33 / 21:34（已解锁并切回前台）仍是 `171`**。进程存活（`pidof` 未变、`ActivityRecord` 在栈顶） |
| 形态 2（R111 首个包） | 熄屏后 21:43:00 起播 `4` → 21:43:51 `56` → 21:46:36（解锁）`226` → 21:47:00 仍 `226`。元素 **`paused === false`**、也没有 `MediaError`：只是位置不动 |
| 形态 3（R111 带僵死看门狗） | 21:53:31 熄屏起播 `4` → 21:58:21 解锁回前台：**进度是 `0`**，核心日志没有新的启动记录、`pid` 也没变 → **WebView 页面被系统整页重载了**（渲染进程被杀后的恢复），播放状态全丢 |
| 三种形态的共同点 | 都不是「进程死亡」：`pidof` 一直在。是**系统的后台策略**在掐「WebView 里的媒体」——先让音频停住（形态 1/2），时间再长一点直接把渲染进程回收（形态 3） |
| 结论 | **P2 必须做前台服务（foreground service）+ MediaSession**：让系统把它当「正在放音的应用」，既不被挂起也不被回收。技术路线定为「WebView 播放 + 保活」，不做原生播放器 |
| 附带结论（形态 3 暴露的） | 页面一旦被重载，**播放状态就全丢了**（当前曲目、进度、队列）。P2 落地时要把「上次在放什么 / 放到哪」持久化并在启动时如实恢复（暂停态、进度、可重试的候选），否则用户切回来只会看到一个空播放条 |

**顺带修掉的中断恢复（本轮，前端）**

- `audio.service.ts`：`play()` 一律走 `tryPlay()`（3 秒上限，三种结局 `ok / rejected / timeout`）——
  **绝不让调用方无限等**（形态 1/2 里 `play()` 的 Promise 既不 resolve 也不 reject）；
  `resume()` 用同一套，超时算 `failed`；新增 `hardRecover()`（**先 reload 再 play**，治「以为在播、位置不动」）。
- 新增 `utils/playbackStall.ts`（纯函数 `isStalled`）：**只判 `paused` 会漏掉形态 2**——
  元素不暂停、不报错，位置却一动不动。判定用「位置在 8 秒内没变」，采样由引擎的 `timeupdate` 维护。
- `useAudioEngine.ts` 看门狗：先看 `isPausedNow()`（→ `resume()`），再看 `isStalledNow()`（→ `hardRecover()`）；
  两条都以「有 `MediaError` 给 2 次重新解析、只有超时/僵死给 1 次」收尾，仍不行就 `markInterrupted()`。
- 新增 `markInterrupted()` 与 `player.failureInterrupted` 文案（中/英）：界面从「假装在播、进度不动」
  变成「播放被系统中断（点播放继续）」，点播放走既有的 `retryPlayback`。
- 冒烟 +3：`isStalled` 的边界（动了/倒退/首次采样都不算僵死）；三种失败各有文案且 `interrupted ≠ media`；
  `markInterrupted` 停表 + 保留曲目。
- **诚实边界**：形态 3 下页面被重载，恢复逻辑没有机会执行——所以这套修复解决的是「页面还活着」的形态 1/2；
  真正让播放活下来要靠 P2 的前台服务。两者的验证分别落在 smoke（逻辑）与真机（§7.4 三种形态）。
