# ADR 0008：第三方登录由插件声明端点，核心只做通用 OAuth 2.0

## 背景

待完成项 6 要求「完善 oauth2 第三方授权登录（抽象 + B 站收藏夹优先）」，而 ADR-0005（第三方中立）
明确禁止在代码、文档、i18n、示例里出现具体的第三方音源地址。两条要求直接冲突：
「优先做 B 站收藏夹」意味着需要 B 站的授权端点，而把端点写进应用就等于内置第三方入口。

同时，社区插件天然是「每家一个」：插件作者最清楚自己那家要走哪套授权（有的要 `appkey`，
有的要 `client_secret`，有的只认自家 TV 接口）。把某一家的协议固化进核心，等于逼着核心为每家
写一遍分支，也让「不推荐任何第三方」变成空话。

## 决策

1. **端点属于插件，流程属于核心**：清单新增 `@oauth`（单文件头部）与 `oauth`（目录包 `plugin.json`）
   声明授权地址、令牌地址、client id、scope、是否 PKCE、回环端口；核心只实现
   「授权码 + PKCE(S256) + 本机回环回调 + 换令牌 + 过期续期」这一段。
2. **授权页由系统浏览器打开**：`auth.begin` 返回 `authorizeUrl`，前端交给 opener；
   应用内不嵌 WebView，用户能在地址栏确认真实域名。核心不依赖 Tauri，也不自己拉起浏览器。
3. **回调只在本机回环**：`127.0.0.1:<随机端口>/callback`，**必须校验 `state`**（不匹配 → 400 且不换令牌），
   等待上限 180s；端口与线程在成功/取消/超时后都释放。
4. **令牌不出核心**：只进 `CredentialStore`（Windows 凭据管理器；不可用时降级为进程内并如实上报
   `backend`），键名 `__oauth_token` 属于宿主保留键——`credentials.get('__…')` 对插件一律返回
   `undefined`；插件唯一的取用方式是 `oauth.getAccessToken()`，且只有声明了 `@oauth` 的插件有值。
   **命令层没有「读令牌」的出口**：`auth.status` 只回「是否已授权 + 过期时间 + scope」。
5. **端点仍是白名单的一部分**：授权/令牌端点的域名必须写在插件 `@hosts` 里、且只允许 HTTPS
   （`http://127.0.0.1` 例外，只用于本地与测试）。不额外开一条「授权可以绕过白名单」的口子。
6. **声明即隐含权限**：`@oauth` 自动补 `network` + `credentials` 两个权限——作者漏写
   `@permissions` 时，授权不该在权限检查处被拒（那只会表现为一句「失败」）。
7. **具体源由插件实现**：B 站收藏夹 = 用户装一个声明了 B 站端点、实现了收藏夹能力的插件；
   核心不为此写任何分支，也不预置任何地址。

## 后果

- 正面：应用保持第三方中立（ADR-0005 不被破例）；新增一家第三方登录不需要改核心；
  令牌的生命周期与落点只有一个实现，审计面很小；核心可独立测试（`core/tests/oauth.rs` 用
  `127.0.0.1` 模拟授权服务器跑完整链路，不连任何真实第三方）。
- 代价：**机密客户端（client_secret）不支持**——公共客户端 + PKCE 是唯一形态；
  需要 secret 的服务只能让用户在插件凭据字段里填，或者等后续 ADR 明确扩展。
  刷新令牌、scope 变更、注销远端令牌（RFC 7009）都未实现，只保证「本地令牌删除」。
- 风险：插件作者若把 `nopkce` 打开、或把回环端口写死成常见端口，安全性/可用性由作者承担；
  界面必须对 `pkce: false` 给出明确提示（已实现），预览阶段也会如实展示声明。
